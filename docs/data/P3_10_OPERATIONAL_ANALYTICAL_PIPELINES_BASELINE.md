# P3.10 Operational and Analytical Data Pipelines Baseline

## Purpose

P3.10 defines the baseline for transforming operational data into analytical, reporting, dashboard, export, and institutional evidence outputs.

This phase does not implement dashboards or claim final data warehouse readiness.

It defines how operational SQL Server data can be converted into controlled analytical outputs without breaking auditability, privacy, longitudinal history, or on-premise constraints.

## Status

Backend production readiness: BLOCKED_PENDING_REAL_EVIDENCE

Backend freeze status: NOT_FROZEN_PENDING_ON_PREM_EVIDENCE_AND_CONTRACTS

## Core principle

SQL Server is the operational source of truth.

Analytical outputs must be derived from governed operational records, longitudinal events, audit trail metadata, and controlled snapshots.

The analytical layer must not become the operational source of truth.

## Pipeline categories

| Pipeline | Purpose |
|---|---|
| operational reporting pipeline | Produce near-operational reports from approved SQL Server views or read models |
| analytical snapshot pipeline | Produce time-bounded, reproducible analytical snapshots |
| dashboard dataset pipeline | Prepare dashboard-ready datasets |
| export pipeline | Generate governed CSV/XLSX outputs |
| evidence package pipeline | Generate sanitized institutional evidence packages |
| quality monitoring pipeline | Track completeness, rejected records, quarantine, and validation issues |
| impact measurement pipeline | Prepare aggregate metrics for social impact analysis |

## Required pipeline metadata

Every governed pipeline execution must preserve:

- pipeline id
- pipeline name
- pipeline type
- source system
- source tables or source views
- source time range
- execution timestamp
- executed by
- organization id
- correlation id
- request id
- input record count
- output record count
- rejected records
- quarantine count
- validation result
- audit trail reference
- snapshot id when applicable
- export id when applicable
- evidence package id when applicable

## Operational source rules

Operational data remains in SQL Server.

Required rules:

- SQL Server on-premise compatibility.
- No cloud dependency.
- No secrets in repository.
- No direct dashboard writes into operational clinical tables.
- No analytical process may silently modify operational data.
- No export may bypass audit trail.
- No report may bypass organization id filtering.
- No analytical snapshot may contain unnecessary sensitive patient data.

## Analytical snapshot rules

Analytical snapshots must be reproducible.

A snapshot must include:

- snapshot id.
- source time range.
- source filters.
- organization id.
- generated at.
- generated by.
- source commit SHA when applicable.
- pipeline version.
- data quality summary.
- audit trail reference.

## Reporting latency classes

| Class | Target use | Notes |
|---|---|---|
| operational | Daily or intra-day operational review | Must stay close to source data |
| tactical | Weekly or monthly program management | Can use snapshots |
| strategic | Direction, board, institutional reporting | Must use governed aggregate evidence |
| research | ODS, impact, causal, Bayesian, or statistical analysis | Must use anonymized or minimized datasets |

## Privacy and minimization

Analytical outputs must use minimum necessary data.

Default outputs should prefer:

- aggregate metrics.
- pseudonymous identifiers.
- synthetic test data for demos.
- redacted evidence.
- date range filters.
- organization-scoped datasets.

Patient-level exports require explicit governance.

## Relationship with P3.8 and P3.9

P3.10 depends on:

- P3.8 SQL Server on-prem operational evidence.
- P3.9 total auditability.
- P3.9 longitudinal history.

Pipelines must preserve:

- audit trail.
- patient timeline.
- consent timeline.
- encounter timeline.
- clinical timeline.
- correction event.
- controlled data injection evidence.
