# P3 OpenAPI Frontend Contract Freeze Baseline

Status: active
Scope: OpenAPI and frontend integration contract freeze
Target phase: P3-30D
Depends on: P3-30C emergency contact and insurance fields contract

---

## 1. Purpose

P3-30D freezes the frontend integration contract before full frontend implementation.

The goal is to prevent frontend, backend, database, and offline sync drift.

This baseline does not create database migrations.

This baseline does not implement frontend screens.

This baseline defines the minimum required API contract stability before the Web/PWA, iOS, and Android clients implement the patient intake, consent/signature, emergency contact, insurance, and offline sync workflows.

---

## 2. OpenAPI position

The backend already has Swagger/OpenAPI support.

The expected development OpenAPI document path is:

- /openapi/v1/openapi.json

The expected development Swagger UI path is:

- /swagger

Swagger/OpenAPI exposure in production must remain controlled by environment and configuration.

Client applications must never connect directly to SQL Server.

Client applications must consume the backend API.

---

## 3. Required frontend contract areas

The frontend contract freeze must cover:

- patient intake;
- consent and signature evidence;
- emergency contact;
- insurance and social security;
- available services per brigade;
- visit creation;
- clinical service encounter capture;
- offline sync batch creation;
- offline sync processing;
- conflict and rejection handling;
- health readiness checks;
- standardized API response envelope;
- standardized API error envelope;
- correlation id behavior;
- authentication and authorization behavior.

---

## 4. Required frontend handoff artifacts

The frontend handoff must include:

- OpenAPI document path;
- Swagger UI path;
- API base URL strategy;
- environment variable names;
- required headers;
- authentication assumptions;
- correlation id header behavior;
- response envelope rules;
- error envelope rules;
- DTO ownership rules;
- field optionality rules;
- offline sync payload rules;
- rejection code mapping;
- frontend validation copy source;
- mock-data allowance;
- production integration restrictions.

---

## 5. Required API response rules

The frontend must expect:

- camelCase JSON;
- standardized success response envelope when applicable;
- standardized error response envelope;
- validation errors with field-level details;
- correlation id returned or traceable;
- HTTP 400 for validation failures;
- HTTP 401 for unauthenticated requests;
- HTTP 403 for unauthorized requests;
- HTTP 409 for conflicts when applicable;
- HTTP 429 for rate limiting;
- HTTP 500 only for unexpected server failures.

---

## 6. Required frontend environment variables

The frontend contract must reserve:

- NEXT_PUBLIC_API_BASE_URL;
- NEXT_PUBLIC_API_TIMEOUT_MS;
- NEXT_PUBLIC_ENABLE_MOCK_API;
- NEXT_PUBLIC_ENABLE_OFFLINE_MODE;
- NEXT_PUBLIC_APP_ENVIRONMENT.

Native clients must use equivalent environment/configuration values without hardcoding production URLs.

---

## 7. Required headers

The frontend contract must define:

- Authorization;
- X-Correlation-Id;
- Content-Type;
- Accept.

Authorization is required for protected operations.

X-Correlation-Id may be generated by the client or returned by the backend.

Content-Type must be application/json for JSON requests.

Accept should prefer application/json.

---

## 8. Frontend implementation boundaries

Allowed after P3-30D:

- Web/PWA frontend scaffold;
- API client scaffold;
- generated or manually typed DTOs from frozen contract;
- patient intake UI;
- consent/signature UI;
- emergency contact UI;
- insurance/social security UI;
- offline queue UI;
- sync status UI;
- mock API mode.

Not allowed after P3-30D without additional evidence:

- production API integration;
- direct SQL Server access from clients;
- storing secrets in frontend code;
- bypassing backend authorization;
- bypassing offline sync contract;
- logging sensitive patient data in browser console;
- treating mock API behavior as production evidence.

---

## 9. Required contract freeze rules

After P3-30D, changes to frontend-facing DTOs must be treated as contract changes.

Breaking changes must require:

- updated product contract document;
- updated OpenAPI/frontend contract freeze document;
- updated tests or verifier;
- migration or compatibility note when applicable;
- frontend approval when frontend implementation already depends on the contract.

---

## 10. Non-goals

P3-30D does not deploy production.

P3-30D does not start frontend implementation.

P3-30D does not execute staging smoke tests.

P3-30D does not claim production readiness.

P3-30D does not expose Swagger in production.

P3-30D does not allow clients to connect to SQL Server.

---

## 11. Acceptance criteria

P3-30D is complete when:

- this OpenAPI/frontend contract freeze baseline exists;
- the OpenAPI/frontend contract freeze document exists;
- the OpenAPI/frontend contract verifier exists;
- OpenAPI/frontend contract tests exist;
- the patient intake contract references P3-30D;
- the consent signature contract references P3-30D;
- the emergency contact and insurance contract references P3-30D;
- the security/product gap audit references P3-30D;
- repository governance validation includes the OpenAPI/frontend contract verifier;
- dotnet build and dotnet test pass.
